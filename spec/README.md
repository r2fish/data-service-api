# Common Data Service API Specification

This directory is the authoritative, platform-independent contract shared by `r2db-api` and `MitateDB-api`.

The target is that an AI agent can use either implementation from:

1. this API specification,
2. a base URL, and
3. an authorized API key.

`data-service-api.v1.json` is intentionally **not** an OpenAPI document. It is a
platform-independent semantic contract — the source of truth for both
implementations. An OpenAPI description of the HTTP surface may be derived from
it for tooling purposes, but any derived artifact is non-authoritative, and the
absence of OpenAPI structure here is a design decision, not a defect.

`data-service-api.v1.json` is the initial machine-readable contract. It covers endpoint semantics, request/response shapes, authentication roles, error codes, structured query/schema operations, finite resource limits, lifecycle, audit semantics, and versioning/compatibility rules. `CCR_DISPOSITION.md` records the formal disposition of CCR-01 through CCR-12.

`CONTRACT_HISTORY.md` is the provenance companion for `data-service-api.v1.json`: every contract value carrying a provenance marker (a "Since 1.x.y", "subordinate ruling N", or similar phrase) gets a `## <json_path>` anchor there, naming that value's full text copied verbatim, the `CCR_DISPOSITION.md` subordinate ruling it refers to, and the contract version that introduced it. Anchors are JSON paths (e.g. `## versioning.version_binding`), not condition or ruling IDs, because that is the only identifier the contract JSON itself offers for a value. The contract JSON carries no reference key pointing at this companion — reaching it is one hop from this `spec/` directory, not one hop from inside the JSON itself, so an agent working from the contract alone should also check what else lives in `spec/`.

Contract 1.7.0 (subordinate ruling 12) moved the provenance-marker text itself out of 26 of those anchored values (`R-10 (B)`), leaving only the numbered decision they refer to inside the contract body; `CONTRACT_HISTORY_MANIFEST.json` records, per `json_path`, exactly what was removed (`stripped_prefix` / `stripped_insert`, plus a single word-level `rewrite`; contract 1.12.0 added a second, whole-value `rewrite` for `limits.audit_requests_per_minute_note`) so that applying it in reverse to the live contract value reconstructs `CONTRACT_HISTORY.md`'s own quote for that path byte-for-byte. Three values could not be mechanically separated this way (`unstripped: true` in the manifest, with a `reason`) and still carry the marker inline in the contract body.

Contract 1.8.0 (subordinate ruling 13) adds no new `## <json_path>` anchor: its 4 marker-free contract values carry no provenance marker of their own (deliberately, continuing R-10 (B)'s direction of keeping the contract body free of provenance text). Their provenance, and 1.8.0's own monitor-finalized anchor sentence, are instead recorded in the existing `## versioning.version_binding` section's "Revision note" -- the same anchor that already covers subordinate ruling 13's own 4th 1.8.0 piece of prose in that section's quote -- so the `## <json_path>` scanner/heading agreement the paragraph above describes is unaffected: 1.8.0 adds no heading and no exception to it. Those 4 are `capability_status.rules`' new array element, the sentence appended to `limits.profile`, `versioning.obligations`' 1.8.0 entry, and — added by 1.8.0's own pre-publication addendum (supervisor ruling U-9, 2026-09-08; "Revision note 2" in the same section) — the sentence pair appended to `structured_operations.idempotency.record`, which likewise gains no anchor of its own.

Contract 1.9.0 (subordinate ruling 14) likewise adds no new `## <json_path>` anchor: its 6 marker-free contract values carry no provenance marker of their own. Their provenance is instead recorded in the existing `## versioning.version_binding` section's "Revision note 3" -- the same anchor that already covers subordinate ruling 14's own 1.9.0 piece of prose in that section's quote -- so the `## <json_path>` scanner/heading agreement the paragraph above describes is unaffected: 1.9.0 adds no heading and no exception to it. Those 6 are the new top-level `common_baseline` section, `capability_status.rules`' new array element, `versioning.obligations`' 1.9.0 entry, `endpoints.operation_catalog`, `schemas.OperationCatalogDocument` and `definitions.OperationCatalogEntry`.

Contract **1.10.0** (subordinate ruling 15, keyset paging) likewise adds no new `## <json_path>` anchor: its new `structured_operations.paging` section (6 keys) and `versioning.obligations`' 1.10.0 entry carry no provenance marker of their own (measured: the marker scanner finds 0 hits on all 7 new/changed values; the raw contract JSON's total scanner-hit count stays exactly 3, unchanged, all 3 the same pre-existing `unstripped: true` paths named above). Their provenance, the `Page.size`-refusal and default-page alignment, and the `Page.cursor` `maxLength` removal (requester ruling Q-5 = (a)) are recorded in the existing `## versioning.version_binding` section's "Revision note 4", "Revision note 5" and "Revision note 6".

Contract **1.11.0** (subordinate ruling 16) likewise adds no new `## <json_path>` anchor: `errors.details_vocabulary.undeclared_field` and `versioning.obligations`' 1.11.0 entry carry no provenance marker of their own (measured: the marker scanner finds 0 hits on both new/changed values; the raw contract JSON's total scanner-hit count stays exactly 3, unchanged). Their provenance is recorded in the existing `## versioning.version_binding` section's "Revision note 7" -- the same anchor that already covers subordinate ruling 16's own 1.11.0 piece of prose in that section's quote. 1.11.0 unifies both peers' refusal for a field name a query's `select`, `where` or `order_by`, or a mutation's `values` or `where`, names but the entity does not declare: `VALIDATION_FAILED`, `violated_declaration: request_schema`, `field` naming the position, with no `declared_type`/`observed_type` -- `NOT_FOUND` is not a conforming refusal of an undeclared field name at these positions.

Contract **1.12.0** (subordinate ruling 17) adds no obligation and no new `## <json_path>` anchor. It changes one existing value, `limits.audit_requests_per_minute_note`: the contract no longer says that `audit_requests_per_minute` is a fixed window. The shape of that window is not defined -- an implementation may count over a sliding 60-second window or over fixed 60-second windows, and admits no more than the declared number of `audit_query` requests within any one window it counts over. Both peers count over a sliding window and their behavior does not change. `CONTRACT_HISTORY.md` keeps the 1.4.0 quote for that path; the manifest entry for it gains a whole-value `rewrite` that reconstructs the quote from the live value. `versioning.version_binding` gains one sentence ("Revision note 8").

Contract **1.13.0** (subordinate ruling 18) adds one obligation and no new `## <json_path>` anchor. It adds `audit.process_loss_policy` (summarized here; the confirmed text is the value at that path): an implementation declaring 1.13.0 or higher, when a service process stops without completing a graceful shutdown, loses neither the audit event of an operation whose response the service had already returned nor the count of any denial occurrence whose response the service had already returned; a buffer that such a stop can empty is therefore not the bounded buffer `audit.sink_failure_policy` permits. The obligation is unconditional (it does not depend on any capability's own status) and is indexed in `versioning.obligations`' 1.13.0 entry; an implementation still declaring 1.12.0 or lower is not held to it retroactively. `audit.sink_failure_policy` is unchanged. The contract states the outcome only and names no mechanism. The new values carry no provenance marker of their own, so their provenance is recorded in the existing `## versioning.version_binding` section's "Revision note 9".

Contract **1.14.0** (subordinate ruling 19) adds three obligations and no new `## <json_path>` anchor. It states, in 7 new contract values, how a client forms a request and reads a response -- `versioning.url_composition` (a request URL is formed from the base URL of the operation's own surface by removing that surface's base path and appending the operation's whole path; no redirect is followed in answer to a request that carries a credential), `endpoint_fields_note.path` (placeholder values and their percent-encoding), `media_type_note`, `errors.response_classification` (every response is classified by its Content-Type's media type), `external_standards` (HTTP, JSON and URI syntax), `schemas.CapabilityDocument.properties.role.description` and `definitions.OperationCatalogEntry.description` -- and it appends sentences to `schemas.CapabilityDocument.properties.operation_catalog_url.description` and replaces one sentence of `schemas.CapabilityDocument.properties.surfaces.description`. The three obligations are unconditional and are indexed in `versioning.obligations`' 1.14.0 entry (summarized here; the confirmed text is the 1.14.0 paragraph of `versioning.version_binding`): every successful response carries `media_type` as its Content-Type, every capability document carries `role`, and a catalog URL that differs from the one `versioning.url_composition` forms is served without a credential; an implementation still declaring 1.13.0 or lower is not held to them retroactively, and `schemas.CapabilityDocument.required` is unchanged. Both peers already meet obligations (a) and (b) -- measured on the four wire plugs -- and no plug declares an `operation_catalog_url` that obligation (c) applies to; their behavior does not change. `CONTRACT_HISTORY.md` keeps the 1.6.0 quote for the `surfaces` path and the manifest entry for it gains a whole-value `rewrite` that reconstructs the quote from the live value; `versioning.version_binding` records the rest in its "Revision note 10".

`OPERATION_CATALOG.json` is a derived, machine-generated artifact: `tools/contract_catalog.py` projects `data-service-api.v1.json`'s `endpoints`/`control_endpoints` entries into one `{name, method, path, roles, requires_capability, atomicity, destructive, request_schema, response_schema}` record apiece, reading structure only (never interpreting prose). It is non-authoritative — the contract JSON remains the source of truth — and is regenerated deterministically; `conformance-tests/test_operation_catalog_register.py` asserts the checked-in file still matches a fresh run of the generator.

Do not treat deployment-specific paths, proxies, database connection mechanics,
or cloud-provider products as part of the common API contract.

The JSON artifact is a contract document rather than a JSON Schema for one
request body: endpoint payload schemas are named under `schemas`, and each
implementation must expose equivalent semantics through its adapter.
