## 2. 確定した判断と根拠

### 2.1 conformance の port/plug 分割

port (抽象 interface と条件テスト) は `conformance-tests/` が所有し、plug (実体接続) は各 peer が所有する。CLAUDE.md の「peer を共通契約の暗黙的所有者にしない」に対応する。

**設計原則として明文化したもの** (`docs/design/CONFORMANCE_ADAPTER_V1.md`):

- negative test には必ず positive control を組にする (全部拒否する adapter が自明に合格するのを防ぐ)
- 「攻撃面が存在しない」主張は署名検査で構造的に証明させる。主張を受理しない
- required adapter の import 失敗は skip ではなく fail (skip は未検証を許可に変える)
- adapter は peer の振る舞いを忠実に写す。**peer の不足を adapter で埋めてはならない** (埋めた時点で suite は実体でなく adapter を検証することになる)

### 2.2 database-per-application (§8, `R2DB_SERVICE_LAYER_ARCHITECTURE.md`)

当初 schema-per-application で設計したが、依頼者の指摘により変更した。

**スキーマは名前空間、データベースは壁。** PostgreSQL は FDW/dblink 無しにデータベースを跨げない。schema 境界は `search_path` の設定ミス、grant の漏れ、RLS の当て忘れのいずれか一つで越えられる。

さらに旧設計には、防ごうとしていた失敗様式そのものがあった。RLS を実行時コードが各テーブルへ付与していたため、将来テーブルを作る経路が増えて付与を忘れれば壁が黙って消える。

SI-00 の Implementation freedom が topology を規定しないため、契約変更は不要、MitateDB への影響も無い。

**必須実装条件**: `REVOKE CONNECT ON DATABASE ... FROM PUBLIC` (新規 DB は既定で PUBLIC に CONNECT が付く。閉じ忘れると壁が最初から無い)。越境接続の拒否は `PostgresCell` 経由ではなく生の接続で検証する。

### 2.3 接続プール上限 (§8.7)

当初「接続数の制約は本配備では効かない」と判断したが誤りだった。アプリ数と `pool_size` の積を計算していなかった。13アプリで104接続、`max_connections=100` を超える。既存本番は既に11アプリある。

**稼働中の旧実装が同じ問題を既に解いていたのに参照しなかった。** `project/r2-vps/apps/r2db-api/src/r2db_api/pools.py` の `AppPoolManager` はアイドル退避と LRU 上限を持つ。設計を移植した。

**本質は上限をアプリ数から切り離すこと。** `pool_size` を下げるだけの対症療法では成長構造が残る。上限は `cache_max × (pool_size + overflow) = 32 × 4 = 128` で、旧実装と一致する。

退避が貸出中接続を閉じないことは構造で担保している (`close_all()` はキューのみ排出、貸出中の接続はキューに存在しない)。

### 2.4 契約への追加 (依頼者承認済み、`f6ce859` に含む)

- `audit.sink_failure_policy` — security-relevant denial と control-plane 変更は fail-closed、通常の data operation event は bounded buffer + 明示的 alert
- `CapabilityDocument.authorization_propagation_bound_ms` (`required` 化を含む)

いずれも CCR-06 / CCR-10 で採用済みの意味論を機械可読にしたもので、新規 CCR ではない。

### 2.5 配備方針 (未実施)

既存 VPS 実装 (作業機ローカルの `project/r2-vps/apps/r2db-api`、公開ホスト名と待受 port は当該実装の nginx / systemd 設定を参照) は現行正本として無変更のまま。新実装を並置する。

**段階1**: 8443 (別ポート、**既存と同じ server_name**)。既存 nginx の `location /` に触れないので、検証段階のミスが本番に出ない。
**段階2**: 問題なければ 443 に path 振り分けを追加し 8443 を閉じる。両実装のパスは**完全に重ならない**ことを確認済み (新実装は6 endpoint、旧の `/v1/tables`、`/v1/meta`、`/admin/api`、`/health` と衝突しない)。

環境変数は**同名で良い** (systemd の EnvironmentFile がユニットごとに分かれるため)。重要なのは名前の分離ではなく、各 EnvironmentFile に全項目を明示し、環境からの継承に頼らないこと。**秘密と DB 接続先は必ず別値**。

## 3. 未決事項 (依頼者判断)

### 3.1 CCR-13/14/15 の採否

第2版起票済み、Fable によるレビュー2回実施済み。**第3版が必要** (§4 参照)。

Opus の推奨は「**安全条項のみ先に採用、endpoint 形状は r2db-api が起動できるまで保留**」。論点の性質が2種類に分かれるため。

| 種類 | 運用経験に依存するか |
|---|---|
| 安全条項 (bootstrap 規則、分離配備可能性、共有秘密の禁止、個別失効可能性) | しない → いま採用可 |
| endpoint 形状 (パス、動詞、req/res 形状) | **する** → 起動後に確定 |

ただしこれは Opus の判断であり決定ではない。「全体を採用」「全体を延期」も選択肢として残っている。

**注意**: 採用側の主論拠だった「乖離は既に3回起きている」は正確でない。統治下の実装2つはどちらも HTTP 制御面を持たず**乖離ゼロ**。3つ目 (旧 VPS 実装) は契約の統治外。乖離は実際の問題ではなく見込みの問題である。

### 3.2 control credential の in-band 発行

盗まれた1本から新しい credential を作れると、**失効を生き延びる永続性**を攻撃者に与える。既存 invariant は control credential の侵害を扱っていない (SI-00 は Application credential についての条項)。

rotate/revoke/disable を HTTP に置く論拠は成立するが、**発行まで in-band である必然は論証されていない**。Vault root の慣行のように、発行を bootstrap 級の帯域外儀式に留める案がある。未決。

### 3.3 その他

- CCR-13: `MutationResult` の拡張を v1 で行うか (サーバ採番識別子を返す唯一の応答形状変更)
- CCR-14: base path を `/control/v1` として `/v1` から分けるか
- CCR-15: またぐ entity 数・操作数の有限境界

## 4. 第3版で直すべき点 (Fable レビュー由来、未着手)

### CCR-13

- **可変 entity へスコープを絞る。** 無条件な普遍的 addressability は新しいゲート。外部表の透過のような再計算される読み取り専用 entity は、どの機構でも安定した識別子を持たない。行を狙った mutation を支持する entity にのみ要求し、読み取り専用・追記専用は宣言により免除する
- **結果を4性質に分解する** (宣言・可視・照準・一意かつ不変)。散文の「同じ行を後から確実に指せる」では適合テストが書けない。**機構が自由なままだと、適合する2実装がクライアントから見た指し示し方で非互換になりうる**
- **revision の被参照先を5条項で固定する** (不透明・行スコープ・実装発行の文字列、commit ごとに変化、mutation と原子的に比較、不一致は `PRECONDITION_FAILED`)。問題として指摘しながら変更表で何も固定していなかった
- `QueryResult` の revision 要求を `revision_preconditions` が有効な場合に限定する
- **SQLite rowid の引用を修正する。** `INTEGER PRIMARY KEY` でない rowid は `VACUUM` で振り直される (実測確認済み)。引用した機構が引用した結果を満たしていない

### CCR-14

- control 面の discovery と versioning の条項 (分離配備時に `/v1/capabilities` が同じホストに無い)
- reset / lockout 意味論 (最後の control credential を失効した場合の復旧経路。現在の endpoint 一覧はそれを防いでいない)
- Application 削除を対象内か対象外か明記する
- in-band 発行の論拠を立て直すか対象外にする (§3.2)
- **延期の選択肢を依頼者に戻す** (Opus が不確実性を断定に変えて消した)

### CCR-15

- **形状を提案していない。** 変更要求になっていない
- **対話的トランザクション (begin/commit over HTTP) を明示的に排除する。** ロックと接続をクライアントの往復にまたがって保持する SI-08 の危険。「堅牢と安全が第一」を掲げる以上、排除しなければならない
- `capability_status` での申告扱いを明記する
- リクエスト形状は機構ではなく契約。「機構は自由」を不完全さの言い訳に使わない

**Fable の指摘のうち1件は誤り。** 「契約側 r2db-api は schema-per-application」は事実に反する (`0003_provision_application.sql:102` が `CREATE DATABASE`)。`PostgresCell` が `schema` 引数を取るのは各 DB 内の `public` を指すため。ただし「CCR で peer の topology を断定するのは不適切」という指摘自体は妥当なので、記述は「Application の保存スコープ内で atomic 単位を閉じられる」に改める。

## 5. 実装の既知の欠落

### 契約側 r2db-api

- **credential が永続化されない。** `CredentialStore` はメモリ上の辞書。再起動で発行済みキーが全消失する。制御プレーンの永続テーブルは `r2dbsvc_registry.applications` のみで credentials テーブルが無い
- **composition root が無い。** `create_app(service)` は `DataService` を引数に取る関数で、uvicorn が指せるモジュールレベルの `app` が存在しない。プロセスマネージャから起動できない
- **全フィールドが JSONB。** 型・主キー・NOT NULL・UNIQUE・DEFAULT が無い。契約の `field_type` は受理して無視している
- 契約が約束済みで未実装: `order_by`、`page`/`next_page`、`alter_field`/`create_index`/`drop_index`、`expected_revision`、`idempotency_key`
- DB ロールパスワードの保持者が未定 (DSN を外から受け取る形にしただけ。旧実装は制御 DB に平文保持しており、新実装はまだ解いていない)

### MitateDB-api

- **HTTP 層が無い。** in-process の Python API のみ。プロセスとして起動する概念が無い
- 保存先が `sqlite3.connect(":memory:")`。プロセス終了でデータごと消える
- **destructive 確認がトークンを検証しない。** `if not confirm:` のみで判定するため任意の truthy 値が通る (`confirm="not-the-real-token"` で削除成功を実測)。修正には「有効な確認とは何か」の契約判断が要る。**C-06 共通 suite 化の前提条件**

### 二実装要件について

MitateDB が HTTP 層を持たない限り、「2つの実装が同じ公開 API を提供する」ことを HTTP 越しに実証できない。conformance suite が in-process adapter でこの差を吸収している。どこかで扱う必要がある。

## 7. Opus がこのセッションで犯した誤り (再発防止のため記録)

1. **接続数の制約を「本配備では効かない」と判断した。** アプリ数と `pool_size` の積を計算していなかった
2. **稼働中の旧実装を読まずに一般論から処方した。** database-per-application、環境変数の共通化、server_name の共有 — いずれも依頼者の直感が正しく、答えは旧実装のコードに既にあった
3. **SI-02 を「HTTP 制御面の禁止」と読み違えた。** 実際の要求は authorization の**分離**であって不在ではない
4. **CCR-13 第1版で `idempotency_key` が行の同一性を前提とすると誤り**、その誤りに基づいて追記専用データから冪等性を奪う提案をした
5. **`upsert` を引用していなかった。** 契約が意味を与えられない操作を既に許可しているという最強の根拠を落としていた
6. **Fable が不確実として提示した判断を、disposition に断定として書いた。** 依頼者から選択肢を消した
7. **変異テストの復元に `git checkout` を使い、未コミットの作業を破棄した。** それまで scratchpad へバックアップしていたのに手順を外した

共通する傾向は **検証せずに助言したこと**。変異注入で検証した箇所 (共有バリデータ、RLS、越境接続、プール上限、契約コピーの drift) は一つも覆っていない。
