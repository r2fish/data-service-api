## 1. 恒久の運用規律

### 1.1 役割とコミット

1. 体制は Fable 監督 (枠付け・判断・commit)、Opus (起草・独立レビュー・受け入れ監査)、Sonnet (実装、commit しない)。(`WO-P8`:7)
2. git commit / push / merge は監督のみが行う。実装担当は commit しない。(`WO-P8`:1125)
3. commit → push → main マージまでを 1 単位とする。(`WO-P8`:1133)
4. main へのマージは `--no-ff` で行う。(`H0829F3`:43)
5. push 前に `git log --format='%an <%ae>' -5` で `r2fish` / noreply のみを確認する。実名・Gmail アドレスが 1 件でもあれば push しない。(`WO-P8`:1126-1132)
6. identity の確認は merge commit にも掛ける。(`H0829F3`:43)
7. identity の確認は commit と同一のコマンドで行う。(`WO-P8`:1126)
8. branch の確認は commit と同一のコマンドで行う (`git -C <worktree> symbolic-ref --short HEAD && git -C <worktree> commit -m "…"`)。(`WO-P8`:1134-1138)
9. コミット前の `git status` / diff stat の突合は監督が行う。(`H0829F4`:39)
10. 契約ファイルを触るコミットは root suite 完走を完了条件にする。(`H0829F4`:35)
11. 申告と実挙動は単一コミットでしか同時に動かさない。(`H0829F`:45、`WO-P8`:1140)
12. 契約変更を実装判断として先行させない。peer を共通契約の暗黙的所有者にしない。(`H0828`:210)

12a. 監督は `git add -A` を使わず、`git status --short` を見て報告に列挙されたパスだけを add する。実装担当が結合された worktree で作業中は commit しない。(監督裁定 2026-09-08。出所はフェーズ10 R-34 の実施 — `docs/design/PHASE10_DEPLOYMENT_EVIDENCE_V1.md` §11.5、`RM`:§8 R-34)

### 1.2 worktree と共有チェックアウト

13. 並行作業は WP ごとの linked worktree (`.claude/worktrees/<name>`) で行う。(`WO-P8`:21)
14. 共有ツリー (リポジトリルートの作業ツリー) を checkout しない。(`WO-P8`:21、1133)
15. マージは専用の別 worktree 経由で行う。(`WO-P8`:1133)

### 1.3 完了ゲートの実行法

19. 完了ゲートは監督がリポジトリルートで単独実行し、その集計行だけを正本にする。(`WO-P8`:1101、`H0907F`:25。出所を 2026-09-07 に再照合し `H0907F`:160 から差し替え)
20. 実行前に `ps` で他の pytest プロセスが 0 件であることを確認する。(`WO-P8`:1101)
21. コマンドは `./.venv/bin/python -m pytest -q -n 5 --dist loadgroup` である (「単独」は他の pytest プロセスが 0 件であることを指し、`-n 5` の worker 数とは別の条件である)。(`WO-P8`:1106。監督裁定 2026-09-07)
22. 合格条件は failed = 0 / skipped = 0 / xfailed = 0 である。(`WO-P8`:1109-1111。CI 上の強制はフェーズ10 WP-1c が入れる — `CI` の集計 step と比較 job の両方。`docs/design/PHASE10_DEPLOYMENT_EVIDENCE_V1.md` §3 D-14、`RM`:§8 R-26)。**CI はこれに加えて `xpassed` > 0 と `deselected` > 0 も赤として扱う** — `xpassed` は宣言が陳腐化した xfail、`deselected` は集計行が suite 全体を表していないことを意味するからである。(監督裁定 2026-09-08。出所はフェーズ10 WP-1c。`docs/design/PHASE10_DEPLOYMENT_EVIDENCE_V1.md` §3 D-14 / §5 U-11、`RM`:§8 R-26)
23. 完了ゲートの前後で `pg_database` の差分を取り 0 であることを確認する。(`H0907F`:163、:25)
24. PostgreSQL テストの残骸を残さない (正常終了・異常終了 `atexit`・起動時 sweep の 3 経路)。(`H0828`:208)
25. `COLLECTION_FLOOR` の値は前回 main の実測値であり、更新は完了ゲートで監督のみが行う。WP の途中で上げない。下げるコミットには理由を commit message に書く。(`H0907F`:159、`CT-README`:185-197)
26. skip は未検証を許可に変える。検証できない条件は skip せず fail させる。(`H0828`:206)。**同じ理由で、宣言が陳腐化した xfail (`xpassed`) と、集計行が suite 全体を表していない状態 (`deselected`) も CI では赤にする** — どちらも「合格の集計が現物を覆っている」という前提を崩すからである。(監督裁定 2026-09-08。出所はフェーズ10 WP-1c。§1.3 の 22 と同じ)
27. 完了ゲートに性能差分を添える (基準値と同じ形式・同じ `--warmup` / `--n`)。(`H0907F`:142、`RM`:135 (P-8))

## 2. 開発機の環境条件

1. 共有 `.venv` を使う (`./.venv/bin/python`、3.11)。システム python を使わない。(`WO-P8`:48)
2. 共有 `.venv` に `httpx2` を入れると完了ゲートの `StarletteDeprecationWarning` は消える。入れていない現状でも 4 数 (passed / failed / skipped / xfailed) は CI と一致するので導入は任意であり、warnings の数は一致判定に用いない。(`H0906F`:115、`H0907F`:27)
3. ローカル PostgreSQL の `max_connections` は 300 である (開発機の設定)。(`H0904F2`:65、`H0907F`:25)
4. ローカル PostgreSQL の `statement_timeout` は 0 である。(`H0907F`:25)
