## 0. 適用の前提と、この手順書が決めないこと

### 0.1 前提

1. **適用元は Q4 フェーズが main へ入った版**である (`2ab012b`)。root suite の実測は **2165 passed / 0 failed / 0 skipped / 0 xfailed** (`pytest -q -n 5 --dist loadgroup`、2026-09-05 に監督が単独実行した完了ゲート)。
2. **両実配備ともフェーズ6 (契約 1.6.0) までのコードで動いている**ことが前提である (`DEPLOY_PHASE6_20260904.md` §8 の実施記録)。**Q4 は migration を当てただけでは完了しない** — 廃止 env の除去とコード入れ替え (r2db = virtualenv 再インストール + 再起動、MitateDB = Q4 コードのイメージで新 revision) が必須である。
3. **順序に強い制約がある。** 本フェーズの新コードは、宣言が無い platform DB では起動しない (F-8 / F-3)。したがって **migration → 宣言 (`ops`) → 廃止 env の除去 → 新コードで再起動**の順に固定する。逆順にすると、新コードのプロセスが上がらない状態が生じる (壊れはしないが、切り戻しの判断を迫られる)。
4. **旧コードは新しい状態と共存できる。** `0008` / `0007` を当てても、既に走っている旧コードのプロセスは env を読み続けて動く (role 設定の既定値 `5000ms` / `5000ms` は旧 env の既定と同一であり、**適用時点で挙動は変わらない**)。**この性質があるので、migration と宣言だけ先に当てて、コード入れ替えを別の窓に置いてよい。**
5. **本適用は契約の宣言値を変えない。** 既定のまま進めれば `visibility_lag_ms` は **11000**、`coalescing_window_ms` は **60000**、`surfaces` は現行と同じ 2 本の base URL である。**変えたい値がある場合は本適用と分けること** — 同時に変えると、止まった原因が「手順の漏れ」か「値の変更」かを切り分けられない。
6. **application DB の数だけ per-application upgrade が要る。** 現況の実測は運用者が §1 で埋める (`{r2db の application 数}` / `{MitateDB の application 数}`)。

## 2. r2db-api (VPS Stage 1) への適用 — [運用者] のみ

**前提**: `0001`〜`0007` は適用済み、Stage 1 の 2 unit (`r2dbsvc-api.service` / `r2dbsvc-control.service`) が稼働している (`DEPLOY_PHASE6_20260904.md` §3)。`R2DBSVC_CONTROL_DSN` は運用者だけが持つ provision 資格である。

### (a) platform 単発 migration `0008` を当てる

```sh
psql "$R2DBSVC_CONTROL_DSN" \
  -v api_role=r2dbsvc_api -v controlplane_role=r2dbsvc_controlplane \
  -f r2db-api/migrations/0008_platform_declarations_and_writer_timeouts.sql
```

**2 つの `-v` は必須である** (role 名を `ALTER ROLE` と `audit_writer_roles` の seed の両方へ同じトランザクションで渡すため)。冪等であり、再実行は timeout を**種の既定値へ戻す** — 値を変えるのは `ops set-platform-timeouts` の役目である。

合格: `r2dbsvc_registry.platform_declarations` が存在し、`audit_coalescing_window_ms` = `60000` と `audit_writer_roles` の 2 行があり、`surfaces` 行は**まだ無い**こと。

### (b) `surfaces` を宣言する

**現行の 2 本の base URL をそのまま宣言する** (値を変えない。`DEPLOY_PHASE6_20260904.md` §3(d) で両プロセスへ配ったのと同じ 2 値):

```sh
python -m r2db_api.ops declare-surfaces \
  --data-base-url <data-base-url> \
  --control-base-url <control-base-url>
```

`<data-base-url>` は `/v1` で終わり末尾スラッシュ無し、`<control-base-url>` は `/control/v1` で終わり末尾スラッシュ無し。形式は書き込み時にも読み出し時にも検査される (到達性は検査しない — 設計 §3.11 の 6)。

### (c) 窓を宣言する (既定のまま)

```sh
python -m r2db_api.ops declare-coalescing-window --ms 60000
python -m r2db_api.ops show-declarations
```

`show-declarations` は表の 3 行と、宣言された各 role の `pg_db_role_setting` を出す。**ここで 3 行が揃っていること**を確認してから (d) へ進む。

### (d) 廃止 env 4 本を**両方の** EnvironmentFile から除去する

`/etc/r2dbsvc/api.env` と `/etc/r2dbsvc/control.env` の両方から、`R2DB_AUDIT_STATEMENT_TIMEOUT_MS` / `R2DB_AUDIT_IDLE_TIMEOUT_MS` / `R2DB_DATA_BASE_URL` / `R2DB_CONTROL_BASE_URL` の行を**削除する** (コメントアウトでもよい。**値を空にするのは不可** — 定義されていること自体が拒否の条件である)。

**1 本でも残っていると、次の起動が F-1 / F-2 で必ず止まる。** メッセージは打つべき `ops` コマンドを示す。

### (e) 新コードを入れて再起動する

virtualenv へ Q4 版を再インストールし、両 unit を再起動する (`DEPLOYMENT_RUNBOOK.md` §2 / §7)。**この適用では宣言値が変わらないので再起動順序は問わない** (値を変える定常運用の順序は §4-4)。

```sh
sudo systemctl restart r2dbsvc-api.service
sudo systemctl restart r2dbsvc-control.service
sudo systemctl status r2dbsvc-api.service r2dbsvc-control.service
```

**上がらなかったら journal の 1 行目を読む** — F-1 / F-2 (env が残っている)、F-3 / F-3c (宣言が無い / control が無い)、F-7 / F-9 / F-10 / F-11 (role 設定と実効値)、F-13 (接続 role が宣言に無い)、F-8 (`0008` 未適用) のいずれかであり、**どれもメッセージが次の一手を示す**。

### (f) per-application 台帳を全 application に当てる

```sh
python -m r2db_api.ops upgrade-applications --dry-run   # 未適用があれば終了コード 4
python -m r2db_api.ops upgrade-applications             # 適用
python -m r2db_api.ops upgrade-status                   # 終了コード 0 = pending 空
```

失敗した application があれば、出力に含まれる `REVOKE …;` を provision DSN で発行してから再実行する (`POSTGRES_PROVISIONING_RUNBOOK.md` §17)。

**(e) の再起動より後に (f) を行った場合、当該 application の cell は F-12 で refuse している。** (f) の後に **もう一度 `r2dbsvc-api.service` を再起動する**こと (検査は cell open 時のスナップショットである)。

Q4 コードのイメージで `mitatedb-data` / `mitatedb-ctrl` を deploy し、**`MITATEDB_DATA_BASE_URL` / `MITATEDB_CONTROL_BASE_URL` / `MITATEDB_AUDIT_STATEMENT_TIMEOUT_MS` / `MITATEDB_AUDIT_IDLE_TIMEOUT_MS` を `--set-env-vars` から外す** (`cloud-run-cloud-sql.md` §6.1 / §6.2 が現在形の例である)。

`mitatedb-ctrl` の `--max-instances=1` は Q4 でも据え置きである (§6.2 の Invariant 1)。

### (d) [監督] traffic を新 revision へ切り替える

```sh

python -m mitatedb_api.ops upgrade-applications
python -m mitatedb_api.ops upgrade-status
```

## 4. 適用後検証 (両 peer 共通)

### 4-0. 宣言が現物と一致している [運用者]

```sh
python -m r2db_api.ops show-declarations
python -m mitatedb_api.ops show-declarations
```

合格: 表の 3 行が揃い、`audit_writer_roles` の各 role の `pg_db_role_setting` に 2 つの timeout があること。

### 4-1. 両 surface の `surfaces` が一致する — **本フェーズ後も必須である**

```sh
diff <(curl -s -H "Authorization: Bearer <application credential>" \
        <data-base-url>/capabilities | jq -S '.surfaces') \
     <(curl -s -H "Authorization: Bearer <control credential>" \
        <control-base-url>/capabilities | jq -S '.surfaces')
```

合格: **差分が無いこと**。

**この突合は Q4 の後も依然として必要である。** 本フェーズが閉じたのは「2 つのプロセスが別々の env を読むこと」であって、「両プロセスが同じ platform データベースを見ていること」ではない — **どちらのプロセスも相手の DSN を知らず、この一致は実装が検証しない** (設計 §3.11 の 7、台帳 LQ4-16、`security/CONTROL_MAPPING.md` SI-14 の点 (12))。差分が出たら、疑うべきは env ではなく**両プロセスの platform DSN が別の DB を指していること**である。

### 4-2. `visibility_lag_ms` が 11000 である

```sh
curl -s -H "Authorization: Bearer <control credential>" \
  <control-base-url>/capabilities | jq '.audit_query.visibility_lag_ms, .audit_query.coalescing_window_ms'
```

合格: 既定のまま適用したなら **`11000`** と **`60000`**。**Q-A / Q-B を動かした場合は `max(statement + idle) + 1000` と宣言窓に一致すること** (両方とも `show-declarations` の値から手計算できる)。

### 4-3. per-application の適用漏れが無い

```sh
python -m r2db_api.ops upgrade-status        # 終了コード 0
python -m mitatedb_api.ops upgrade-status    # 終了コード 0
```

合格: **どの application にも `pending` が無い**こと (終了コード `0`)。`4` が返ったら §2(f) / §3(e) へ戻る。

**この確認は以後の毎回の配備の pre-flight に入れる** — 適用漏れは、クライアントからの「503 が返る」という報告ではなく、この 1 コマンドで先に見つける。

### 4-4. 宣言を変えるときの再起動順序 (以後の定常運用)

- **timeout を縮めるとき: data-plane を先、control を後。**
- **timeout を伸ばすとき: control を先、data-plane を後。**

逆順にすると、宣言された `visibility_lag_ms` が実際の書き手接続の bound より**短い**窓が生じ、宣言 lag だけ待ってポーリングする消費者 (C-09) が**まだ見えていない行を見逃す**。過渡のずれ自体は消せない (設計 §3.11 の 10、LQ4-17) — **危険な向きだけを順序で避ける。**

### 4-5. 契約が変わっていないこと

`capabilities.contract_version` が両 peer とも **`1.6.0`** のままであること。Q4 は契約無変更である (U-1)。

## 5. ロールバック

### 5.1 戻せるもの

- **コードの版**: 旧 revision / 旧 virtualenv へ戻す。**ただし旧コードは廃止 env を読むので、戻すなら env も同時に戻す** (旧コードは宣言表を読まないが、`surfaces` を env から得るため)。
- **宣言の値**: `ops` で書き戻し、両プロセスを再起動する (順序は §4-4)。

### 5.2 戻さなくてよいもの

- **`0008` / `0007` (platform 単発)**: 旧コードは role 設定を読まないので、当てたままでも旧コードは動く。役割は timeout の既定値を role へ固定することであり、**その値は旧コードの env 既定と同一である**。
- **per-application 台帳 (`0009` / `0008`)**: 旧コードは台帳を読まない。表が増えるだけであり、catalog / RLS 監視 / `schema_objects` の会計からは除外されている。

### 5.3 戻せないもの

- **一括適用の途中で失敗した application に残る developer role membership** — `REVOKE` を手で発行するまで残る (設計 §3.11 の 8、LQ4-14)。ops の出力に文が含まれる。
