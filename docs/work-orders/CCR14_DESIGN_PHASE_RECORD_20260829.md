## 2. 依頼者検討の経緯と言明 (2026-08-29、時系列)

1. **Q-1 たたき台への評価**: 破壊的確認の「宣言と復唱」方式 (状態レス二段階) について「API の仕様としてはとても良い」(依頼者言明、2回強調)。ただし未裁定のまま — 正式裁定は別途
2. **構造的限界の指摘 (依頼者)**: 「組織内でテストや練習用に作成されたアプリの、作成者の意図しない revoke も通ってしまうのでは」→ 監督が「あらゆる in-band 確認の構造的限界」と認め、依頼者も同意。**確認機構の守備範囲は『要求の曖昧さの排除』まで**が両者の合意として設計 §0.5 に固定された
3. **「人はそれを行う」前提の要求 (依頼者)**: 「control credential をテストアプリが持つべきでない、はその通り。ただ、人はそれを行う。悪意のある人に渡る可能性もある。マヌケ対策として何か用意できないか。失効 (無効化) させられた control credential の復活手段の提供とか」→ R-11 の成立。復活手段は**非対称**で確定: disable には CLI break-glass の enable/rotate を用意、**revoke の復活 (un-revoke) は意図的に作らない** (監査事実の偽化 = SI-13 空洞化。正準の復旧は reset)
4. **抑止の着想 (依頼者)**: 「悪意ある侵入を諦めさせる仕組みは用意できないか。生成 AI の安全フィルターの拒否文のような」→ 監督の回答: API に意図の判定器は置けない (正規と悪意の要求は構文上同一) が、**真実の宣言**を攻撃者側の AI エージェントに読ませてそのエージェントの安全学習を発火させることはできる
5. **期待効果の確定 (依頼者言明)**: 「期待する効果は、ユーザー側のエージェントが警告を発する・注意を促す、で十分。悪意のない人間を慎重にさせる効果があり、悪意のある人間も『このシステムは面倒くさそう』となることが期待できる」→ この水準で設計 v1.3 に固定。虚偽の宣言は禁止、安全はこの層に依存しない
