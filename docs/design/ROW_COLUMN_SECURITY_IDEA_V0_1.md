- 状態: **構想メモ・非正本・保留中**。設計・契約・conformance tests・実装のどれの根拠でもない。台帳は計画文書 `docs/design/ROADMAP_POST_PHASE7_V1.md` §8 の **R-43**。
- 起票: 2026-09-15、依頼者との対話の要約。
- 改版: v0.1 (2026-09-15) 起票。v0.2 (2026-09-15) §8 に起草者の評価を追加し、§6 の先頭に「具体的な利用先」を置いた（依頼者の指示）。
- 保留の理由（依頼者、2026-09-15、逐語）: 「まだ進めなくて良いです。」「data-service-apiには先に実装しならないものがまだあるからです。」
- 公開規律: 例のテーブル・役職は合成例であり、実データではない。

## 1. 依頼者の要求（要約）

権限データ（属性データ）で、行と列の単位でアクセスを制御する。

- 一般データの例:
  - A テーブル: 社員（社長・部長・課長・社員）
  - B テーブル: 列 a・列 b・列 c を持つレコード
- 通常のアクセスで見えるのは一般データまで。
- 列の権限は役職ごとに「読」または「読書」を与える。例: 列 a は部長が読書・社長が読、列 b は課長が読書・社長と部長が読。
- 社員としてアクセスする人（端末）は、許された列（例では列 c）しか見えず、**他の列（列 a・列 b）があることを知らない**。
- 権限データはシステムテーブルに置き、admin のアクセス（または追加の認証を経たアクセス）だけが扱う。

## 2. 依頼者裁定（2026-09-15、逐語）

- 「A テーブルの役職の値は、システムテーブル側に持つ（推奨）で良いです。」
- 「行単位の制御も範囲に入れます。」

## 3. 現状（2026-09-15 時点、契約 1.8.0）

- ロールは固定の 4 つ（`runtime` / `developer` / `control` / `audit`）で、操作単位の許可だけがある（`spec/data-service-api.v1.json` の `security.roles`、`spec/OPERATION_CATALOG.json` の `roles`）。
- 契約にはエンドユーザー・テナントといった主体の概念が無い。主体は「アプリケーション＋ロール」までである。
- エンティティ・行・列の単位の権限も、独自ロールも無い。
- r2db-api は PostgreSQL の RLS をアプリケーション分離にだけ使い、MitateDB-api は使っていない。DB 側の RLS 機能は共通の手段にならない。

## 4. 構想（未確定の候補）

```
一般データ（runtime / developer がデータ API で扱う）
  A テーブル: 社員
  B テーブル: 列 a・b・c
システムテーブル（control が専用 API で扱う。audit は読み取りのみ。データ API からは存在自体が見えない）
  主体の紐付け: クレデンシャル（端末）→ 社員 → 役職
  列の権限: 列 × 役職 → 読 / 読書
  行の規則: 行の属性（例: 所属課）と主体の属性の突き合わせ
```

- **判定の場所**: 構造化 API の層で両 peer が同じ判定を強制する。r2db-api が PostgreSQL の RLS を多重防御に併用するのは任意。
- **列の権限は列ごとに明示する**。役職の上下（レベル以上）では表せない（例では課長が列 a を読めず、列 b は課長が書けて部長は読むだけ）。
- **主体の証明**（候補・未裁定）: control が端末ごとにクレデンシャルを発行し、社員に紐付ける。今のクレデンシャル発行・失効・ローテーションの延長で、新しい信頼境界を作らない。署名トークンの発行者を登録する方式は代替案。リクエスト内の「役職」の値は権限の根拠にしない（SI-06）。
- **権限データと役職の値の変更**: control だけが専用 API で行い、監査に残す。一般データ側から書き換えられる経路を作らない（役職を一般データに置くと、社員が自分を社長に書き換えられる。これが §2 の裁定の理由）。
- **読み取り**: 読めない列は結果にも catalog にも出さない。
- **検索条件・並べ替え**: 読めない列の指定は拒否する（`eq` の反復で値を推測できるため）。
- **書き込み**: 書けない列への書き込みは黙って捨てず、要求全体を拒否する。
- **行**: 検索・update / delete の対象・insert / upsert の書き込み時検査のすべてに行の規則を掛ける。

## 5. 存在を推測させないための要件

見えない列・行について、次のどれからも存在を区別できないこと。conformance で「存在しない列・行と区別できない」ことを確かめる。

- エラー: 読めない列の指定が、存在しない列の指定と同じ code・details になる
- catalog・スキーマのリビジョン・dry_run の結果
- insert: 見えない必須列が原因の失敗（既定値などの規則が要る）
- 一意制約違反・upsert の衝突
- 行の件数・行のリビジョン前提条件
- 冪等キーの replay（別の主体へ他人の結果を返さない）
- 監査ログの検索結果・エンティティをまたぐ変更

## 6. 着手前に決めること

最初に、**具体的な利用先**（どのアプリで使うか、利用者がどう認証されるか、役職以外にどの属性が要るか）を固める。以下の 1〜3 はそれでほぼ決まる（§8.3）。

1. 主体の証明方式（端末クレデンシャルか、署名トークンか）
2. 行の規則の表現（どの演算子・どの属性まで許すか）
3. `developer` のスキーマ操作と権限規則の関係（規則の回避経路を作らない）
4. 見えない列の既定値と一意制約の扱い
5. SI-06 の拡張で足りるか、「存在を推測させない」を独立の不変条件にするか
6. capability 名、契約の版、catalog での規則の見せ方（主体ごとの見え方）
7. 性能: 規則の解決のキャッシュ、行の規則が使う列の索引

## 7. 進め方（着手時）

依頼者が指定する先行項目の完了後に着手する。順序は `CLAUDE.md` の開発順序（共通の要求 → Security Invariants → 共通契約 → conformance → 両 peer の実装）に従う。契約を触るので設計レビューは 2 回。

## 8. 起草者の評価（2026-09-15、Claude。依頼者裁定ではない）

総評: 方向性は良く、依頼者の目標（AI にとって最良の DB、人から見て比類ないセキュリティ）に合う。ただし今までで最も重い契約変更になり、着手前に固めるべき弱点が 3 つある。

### 8.1 良い点

- **この構造の API だからこそ抜け道なく強制できる。** SQL を受け付けず全操作が構造化 API を通るので、サーバーが条件を足せば迂回路が無い。SQL を許す製品の RLS より強い保証を出せる。
- **利用者が AI エージェントであることと相性が良い。** 権限の判定をクライアントのコードに任せると、エージェントが実装を忘れたり誤ったりする。サーバーが強制すればその心配が無くなる。
- **「存在を推測させない」は差別化になる。** 一般的な DB の列権限は「権限がありません」と返し、列の存在は分かってしまう。そこまで塞ぐ製品は多くない。
- **権限の置き場所が正しい。** 権限データも役職の値も control だけが変更でき、利用者が自分に権限を付ける経路が無い。

### 8.2 懸念点

1. **「推測させない」を完全には保証できない面がある。**
   - 応答時間の差や、件数上限に掛かるかどうかの差からは、見えない行の存在を推測できる。
   - 見えない列に一意制約があると、insert の衝突から値の存在が漏れる。原理的に避けられない。
   - 「何を保証し、何を保証しないか」を契約で明示しないと過大な約束になり、信頼性の目標に反する。制約の側でも、見えない列には一意制約を置けない、といった規則が要る見込み。
2. **主体の扱いが今の設計に対して大きな変更である。**
   - 今のサービスは「アプリケーション」を単位にしており、そこに「人・端末」を持ち込むことになる。
   - 端末ごとのクレデンシャルは単純だが、利用者が SSO でアプリにログインする形や共用端末とは対応が合わない。いずれ署名トークン方式が必要になり、認証基盤を作り直す方向に引っ張られる恐れがある。
3. **「役職」だけのモデルは実際の組織には狭すぎる。**
   - 兼務、代理、所属部署、期間限定の権限などが出てくる。行の規則も「所属課」のような役職以外の属性を必要とする。
   - システムテーブルは「役職」に固定せず、**汎用の主体属性**として設計すべきである。

### 8.3 コストと再開時の最初の一歩

- **コスト**: 影響はほぼ全操作に及ぶ（検索、変更、エンティティをまたぐ変更、upsert、冪等性、dry_run、監査、catalog、スキーマ操作）。適合テストの量も最大規模になる。先行項目を優先して保留にした判断は妥当である。
- **最初の一歩**: 計画文書はフェーズ11 以降を「実需駆動」としている。まず具体的な利用先（どのアプリで使うか、利用者がどう認証されるか、役職以外にどの属性が要るか）を固める。これで懸念 2 と 3 はほぼ答えが出る。懸念 1 はその上で保証の範囲を定義する。
