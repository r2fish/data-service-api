## 1. 問題と裁定

| 実測 (2026-09-14、両 peer `src/`) | 値 |
|---|---|
| 総行 / code / comment / docstring | 43,425 / 21,035 / 10,740 / 11,650 |
| 10 行以上のコメント塊 | 355 件 (上位: MitateDB `cell.py` 65 件 1,228 行、MitateDB `http.py` 29 件、`backend_postgres.py` 26 件、r2db `postgres.py` 26 件、`structured.py` 24 件) |
| 経緯トークン | `WP-` 1,581、`Phase` 718、`R-` 509、`review` 441、`round` 199、日付 234 ほか |

コードを読む者 (AI エージェントを含む) は、現在の理由を読むために経緯を読み分けなければならない。

**依頼者裁定 (2026-09-14、逐語「全て推奨で進めてください」、問い 3 = A)**: 経緯は設計書などの記録へ移し、コード内には現在の理由と記録への参照 ID だけを残す。移動は抽出とは別の変更セットで行う。

**目的**: コードには現在の理由だけが残る。経緯は失われず、ID から 1 hop で辿れる。

## 2. 決定事項

### D-1 受け皿

| 案 | 内容 | 評価 |
|---|---|---|
| **(i) 採用** | peer ごとの companion `docs/code-history/<peer>/<module>.md` と、登録 helper 用の `docs/code-history/pair.md`。節見出しは `## CH-NNNN` | 受け皿は 1 種。塊を逐語で丸ごと置けるので照合が単純。移した文の設計書 § / 台帳 ID はそのまま残り、既存記録へも辿れる |
| (ii) 却下 | 既存の設計書 § / 台帳 ID を直接参照する | 経緯の多くは既存記録に逐語で存在せず、1 塊が複数の出所を束ねるので ID が定まらない |

## 3. 判定基準

**範囲**: 両 peer の `src/` だけ。`tests/` と `conformance-tests/` は対象外 (後者に触れると Class C)。

| 区分 | 対象 |
|---|---|
| **残す** | 現在も成立する理由。不変条件。安全上の注意 (lock / transaction / timeout の順序、fail-closed の理由)。外部仕様の挙動。**出所を明示した参照だけ** (v0.3): SI-、C-、spec §、設計ファイル名を付けた § / D- / 局所 ID、`roadmap R-NN` / `roadmap L-NN` の形で書いた台帳 ID。**版数付きの文書名** (`contract <版数>` / `design <版数>` / `<文書名> v<版数>`) と同じ括弧又はラベルにある ID も出所付きとし、(4) でも (6) でも消さない (v0.5 訂正) |
| **移す** | 経緯の叙述 (「以前は X だった」、却下案の検討、裁定に至る議論)。**経緯のトークン**: WP-、review、round、指摘番号、差し戻し、監督裁定、日付。**出所を持たない裸の局所 ID** (例: r2db `postgres.py` の `R-1`〜`R-7`) (v0.3) |
| **対象外** | 実行時に使われる文字列 (argparse の `help=` など)。`# type: ignore` / `noqa` / `pragma` / shebang / encoding 行。登録 helper (`_ISOMORPHIC_TARGETS` の行) は最後の専用変更セットまで触れない (§6)。行末コメント (`x  # ...`) も移動の対象外である。ただし追加された行の経緯トークン検査 (§4.1 (5)) は行末コメントにも掛かる (v0.4) |

| 境界例 | 扱い |
|---|---|
| 1 文に現在の理由と経緯の叙述が同居する | 残す。塊全体は受け皿にも置く |
| 残す文の括弧内に経緯のトークンだけがある | §4.1 (4) の機械的削除で消す (言い換えではない) |
| 台帳 ID の開閉 | ツールでは判定しない。変更セットの manifest に塊ごとの判定表 (塊 / 判定 / 根拠) を置き、レビューで確認する (v0.3) |
| 判定に迷う | **残し、判定表の根拠欄にその旨を書く** |
| docstring が body の唯一の文 | 削除しない (body が空になり AST が変わる) |

**記録**: 変更セットごとに、触れた module の経緯トークン数の前後を manifest に残す。

**現行条項への参照**: 出所の無い条項 ID は裸の ID として消せる。現行の条項を参照として残すときは、コード側で出所を明記する (例: `contract 1.7.0 D-5`) (v0.6、§9 の 5)。

**削除前の確認 (v0.6 追補、監督裁定)**:

- 文を削除する前に、残す文の指示語 (`such` / `this` / `that` / `instead` / `exactly as` / 「その」「これ」など) が、削除する文を参照していないか確認する。参照していれば、その文は削除しない。
- 経緯と現在の理由 (特に安全上の理由) が同居する文は、文ごと残す。
- この規律は、変更セット 1 のレビューで見つかった誤削除 (CH-0069 / CH-0071 のロックモードの理由、CH-0017 の `such` の参照先) を受けたものである。変更セット 2 以降の判定表には、この確認の列を設ける。
- **追補 (監督裁定)**: 点検語に副詞 `again` / `still` / `also` / `instead` / `otherwise` / `then` と「再び」「なお」を加える。変更セット 2 で、残した文の「flipped again」が削除した文を指していたためである (CH-0142)。
- 経緯と現在の規則・防護の説明が同居する文は削除せず、トークンだけを機械的に消す。CH-0178 / CH-0142 の誤削除を受けて、上の既存規律を再確認するものである。

**別件 (対象外)**: 他文書が引くコード位置 (`security/CONTROL_MAPPING.md:41`、`conformance-tests/CONDITIONS.md:53`、`spec/CCR_DISPOSITION.md:156`) のずれは既に存在しており、直すと Class C / D になる。

## 4. 照合と常設検査

### 4.1 変更時の照合 (`check_comment_provenance.py --base <rev>`)

| # | 照合 | 方法 |
|---|---|---|
| (1) | コード不変 | docstring (Module / ClassDef / FunctionDef / AsyncFunctionDef 先頭の文字列定数) を除いた `ast.dump(include_attributes=False)` を旧版と新版で比べる。行送りでは赤にならない |
| (2) | 移した塊が逐語で在る | 新版の `CH-NNNN` ごとに、その節の fenced block が旧版の塊 1 つ (dedent 後) と byte 一致する。旧版の塊のうち、新版に同一の塊が無く、どの CH-ID にも対応しないものがあれば赤 (v0.3)。docstring の照合は `inspect.cleandoc` を適用した後の値どうしで行う。ソースの生バイト列を直接比べるのではない (v0.4) |
| (3) | 文区間の削除だけ | 新しい塊の文の列が、旧い塊の文の列から、順序を保って文を削除しただけのものである (参照行と (4) を除く)。**前処理**: コメント塊は各行の `#` と先頭空白を除いて空白 1 つで連結し、docstring は行を連結する。**区切り**: 文末の句読点 (`. ` / `。` / `? ` / `! `) と空行 (段落境界。コメント塊では中身の無い `#` 行) だけ。改行では切らない。コード span の中と略語 (`e.g.` / `i.e.` / `vs.` / `...`) では切らない |
| (4) | 括弧内トークンの機械的削除 | 残した文の中では次の操作だけを許す: `(...)` の中身が消してよい語と区切り (`, ` `/` `;` 空白) だけなら、直前の空白と括弧ごと消す。出所を明示した参照と同居する場合は、消してよい語 1 個とその区切りを消す。**消してよい語** (v0.3): (5) の語、及び同じ括弧に出所語 (ファイル名 / `roadmap` / `spec`) を持たない裸の ID (SI- / C- / CCR- を除く) |
| (5) | 経緯を足していない | 差分で追加された行に、次の明示リストの語が無い (v0.3): `\bWP-[0-9A-Za-z-]+`、`\bPhase \d+`、`\b(review\|reviewer)\b`、`\bround \d+\b`、`\b20\d\d-\d\d-\d\d\b`、`差し戻し`、`監督裁定`、`supervisor ruling`、`\bblocker\b`。R- / L- / D- の類は入れない (§3 の判定表で扱う)。閉じた ID の一覧はツールに渡さない |

### 4.2 常設の検査 (`check_comment_provenance.py --register`、v0.3)

1. 各 peer の `src/` に在る `CH-NNNN` の集合が、受け皿 (その peer の companion と `pair.md`) の見出しの集合と一致する (未解決 0、孤児 0)。
2. **両 peer の companion と `pair.md` をすべて読み、同じ `CH-NNNN` の見出しが全体で 1 回だけであること。**
3. 各節が非空で、移動元・親コミット・種別の行を持つ。各 ID はその peer の `src/` に 1 回だけ現れる。`pair.md` の ID は、登録行の両側に 1 回ずつ現れる。
4. 参照行の書式は D-2 の 2 形だけ。
5. `src/` の `__doc__` / `inspect.getdoc` / `inspect.getsource` の使用箇所の集合が、変更セット 0 の実測で固定した集合 (空集合) と一致する (docstring に依存する実行時挙動の新設を検出する)。
6. 非空虚: 両 peer を通した ID の総数が定数 `MIN_CH_IDS` 件以上。変更セット 0 では 0、**変更セット 1 で 1 に切り替える**。

自己テストは `tools/tests/test_comment_provenance*.py` の 1 か所に置き、実リポジトリへの `--register` を含む (D-3)。

## 8. 追補: 文頭の経緯ラベルの削除 (v0.5、§4.1 (6))

**本節は v0.5 の追記である。** 変更セット 1 (r2db `postgres.py`) では、移せた塊が 156 中 3、経緯トークンは 113 → 109 だった。10 行以上の塊の多くは「Ruling X (WP-Y): 現在の理由」の形で、§3 の「同居文は残す」に当たるからである。これでは問い 3 の目的を果たせないので、監督裁定 (2026-09-14) により許容操作 (6) を足す。

### 8.1 定義

| 項目 | 規則 |
|---|---|
| ラベル | 文の先頭から、最初の区切り (`: ` / `：` / ` -- ` / ` — `。コード span の外でだけ探す) までの部分。次の 3 条件を**すべて**満たし、除外 1・2 に当たらないもの |
| 条件 1 | §4.1 (5) の経緯トークン、又は出所の無い裸の ID (§4.1 (4) の「消してよい語」の ID と同じ) を 1 つ以上含む |
| 条件 2 | 12 語以下 (日本語は 24 文字以下) |
| 条件 3 | 経緯トークン・ID・括弧・接続語 (`and` / `or` / `、`) 以外の内容語が 3 語以下 |
| 除外 1 | 否定語 (`never` / `not` / `no` / `must not` / `don't` / `cannot`、`ない` / `禁止` / `しない`) を含む。否定は意味を担うため |
| 除外 2 | 保護された参照 (SI- / C- / CCR-、又は同じラベルにファイル名・`roadmap`・`spec`・版数付きの文書名 (§3) を持つ出所付きの ID) を含む。現行の正本への参照であるため |
| 削除の範囲 | ラベルと区切りだけ。区切りの後ろは逐語で残す (先頭の小文字化などの変形もしない) |
| 記録 | 削除を含む塊は、塊全体を受け皿に親コミット時点の写しとして置き、コード側は `# history: CH-NNNN` で参照する (D-2、§4.1 (2) のまま) |
| (4) との併用 | 許す。適用順は (6) → 残った文に (4) (監督裁定 2026-09-14) |
| 照合の受け入れ | 新しい文が「旧文から先頭ラベルと区切りを除き、(4) の削除規則を当てた結果」と完全に一致する |
| §3 との関係 | 同居文がラベル形なら (6) を適用する。ラベル以外の部分に経緯が同居する文は、従来どおり残す |

**語数の数え方 (条件 2・3、監督裁定 2026-09-14)**:

- 語は空白区切りで数える。コード span (backtick で囲んだ範囲) は全体で 1 語。
- 経緯トークンと出所の無い裸の ID は 1 語とし、内容語には数えない。括弧の中身は、括弧を外してから同じ規則で数える。
- 保護されていない裸の ID 又は経緯トークン (例: `WP-6d (ii)`) の直後に括弧付きの枝番 (`(4)` / `(ii)` など、括弧の中が数字かローマ数字だけのもの) が続く場合は、まとめて 1 語とし、内容語には数えない。
- 記号だけの語 (`(` / `)` / `,` など) は数えない。`and` / `or` は内容語に数えない。
- 日本語は、経緯トークン・ID と括弧の文字だけを除いた文字数で数える (24 文字以下)。括弧の中身は数える。日本語を含むラベルにも 12 語の上限を当てる。
- 例: `Ruling U-7 (WP-6d)` → 語 3、内容語 1。枝番付きの `Ruling U-7 (WP-6d (ii)):` → 語 3、内容語 1 (`Ruling`)。`Contract 1.7.0 (D-2 (4), WP-2a):` → 削除不可 (版数付きの文書名。除外 2)。

## 9. 変更セット 0c: 規則の穴の修正 (v0.6)

**一般則**: 許容操作 (3)(4)(6) と §9 の規則はすべて許可であり、照合は、許可された操作の任意の部分集合で導ける新版を受け入れる。無変更の既存コードは常に照合を通る。部分集合の受理は部位 (括弧・ラベル・文区間) ごとに独立に判定し、部位ごとに「そのまま」か「許可された削除を適用」かを照合する。文の長さに上限は設けない。
§4.1 (5) の追加行検査の対象は、基点の塊に無かった経緯トークンだけとする (トークン単位の差分)。基点に元からある経緯トークンを残す部分削除は、この一般則により許容する。
括弧内の区切り (`, ` / `/` / `;` / 空白) は、隣の語を削除したときに 1 つだけ伴って消えてよい。区切りだけを書き換える、又は残すことは許容操作に当たらない。
